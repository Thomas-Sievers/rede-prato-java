# Rede de Prato

Sistema de apoio à redução do desperdício de alimentos e à segurança alimentar. A solução conecta **ofertantes** (feirantes e supermercados) a **beneficiários** (pessoas, famílias, instituições e pequenos negócios), permitindo a disponibilização de alimentos excedentes por doação ou venda com desconto.

> **Observação importante:** este README diferencia o que já está implementado nos scripts Oracle do que é aplicado pela camada de negócio do backend Java. Algumas regras dependem de validações transacionais e, por isso, não ficam apenas no banco de dados. A seção 8 descreve o backend.

**Links:**

- Repositório do backend: https://github.com/Thomas-Sievers/rede-prato-java
- Aplicação publicada: https://rede-prato-java.onrender.com (saúde da API: `/api/health`)
- Documentação interativa da API: https://rede-prato-java.onrender.com/swagger-ui.html

## 1. Objetivo

A Rede de Prato registra alimentos excedentes ainda próprios para consumo, permitindo que sejam reservados e retirados por beneficiários ou destinados à compostagem quando não puderem mais ser consumidos.

A solução busca:

- reduzir o descarte de alimentos;
- ampliar o acesso a alimentos frescos e de baixo custo;
- apoiar famílias e instituições em situação de vulnerabilidade alimentar;
- registrar alertas de novos lotes e oportunidades de xepa;
- produzir indicadores de impacto, principalmente os quilogramas destinados ao consumo ou desviados do descarte.

## 5. Funcionalidades implementadas no modelo de dados

### 5.1 Cadastro de endereços

- Permite reutilizar um mesmo endereço para mais de um ofertante ou ponto de distribuição.
- O endereço é obrigatório para ofertantes e pontos de distribuição.
- O endereço é opcional para beneficiários, contemplando pessoas sem endereço fixo.

### 5.2 Cadastro de ofertantes

- Registra supermercados e feirantes.
- Controla se o ofertante está ativo.
- Registra a existência do selo de parceiro e a data em que foi concedido.
- A restrição `CK_RP_OFERTANTE_SELO_DATA` impede inconsistências entre `possui_selo` e `data_selo`.

### 5.3 Cadastro de beneficiários

- Atende pessoa, família, instituição e pequeno negócio.
- Registra a quantidade de pessoas atendidas, quando aplicável.
- Para o tipo `PESSOA`, a quantidade deve ser igual a 1.
- Mantém exclusão lógica por meio do campo `ativo`.

### 5.4 Cadastro de pontos de distribuição

- Registra cozinhas solidárias, ONGs e associações.
- Mantém os dias e horários de funcionamento.
- Permite que a retirada seja feita em um ponto parceiro ou diretamente no ofertante.

### 5.5 Cadastro e disponibilização de lotes

- Registra descrição, peso, condição, modalidade, preço, valor estimado, datas e status do lote.
- Aceita as modalidades `DOACAO` e `VENDA`.
- Em uma doação, o preço deve ser nulo.
- Em uma venda, o preço deve ser maior que zero.
- Mantém o valor estimado de mercado para apoiar relatórios de impacto e documentação da doação.

### 5.6 Reserva e retirada

- Liga um beneficiário a um lote.
- Permite associar opcionalmente um ponto de distribuição à reserva.
- Registra a data de retirada quando o status da reserva é `RETIRADA`.
- Mantém o histórico de reservas canceladas e retiradas.

### 5.7 Alertas

- Registra alertas de `NOVO_LOTE` e `XEPA`.
- Permite os canais `APP` e `WHATSAPP`.
- O envio real de WhatsApp é simulado no MVP; o banco registra o evento do alerta.

### 5.8 Destinação final

- Registra a destinação `CONSUMO` ou `COMPOSTAGEM`.
- Permite mais de uma destinação para o mesmo lote.
- Gera a base para indicadores de peso destinado ao consumo e peso compostado.

## 6. Algoritmos e regras de negócio

### 6.1 Algoritmo de criação de reserva

**Objetivo:** garantir que um lote disponível receba apenas uma reserva ativa por vez.

```text
receber idLote, idBeneficiario e idPonto opcional
buscar lote pelo idLote

se lote nao existir:
    retornar erro 404

se lote.status for diferente de DISPONIVEL:
    retornar erro de negocio

verificar se ja existe reserva com status ATIVA para o lote
se existir:
    retornar erro 409 - lote ja reservado

criar reserva com status ATIVA
atualizar lote.status para RESERVADO
confirmar a transacao
```

**Proteção no banco:** o índice único condicional `UX_RP_RESERVA_ATIVA_LOTE` impede a persistência de duas reservas ativas para o mesmo lote, inclusive em caso de concorrência.

---

### 6.2 Algoritmo de cancelamento de reserva

**Objetivo:** devolver um lote reservado à disponibilidade quando a reserva for cancelada.

```text
receber idReserva
buscar reserva pelo idReserva

se reserva nao existir:
    retornar erro 404

se reserva.status for diferente de ATIVA:
    retornar erro de negocio

alterar reserva.status para CANCELADA
atualizar lote.status para DISPONIVEL
confirmar a transacao
```

---

### 6.3 Algoritmo de confirmação de retirada

**Objetivo:** registrar que o beneficiário retirou o lote reservado.

```text
receber idReserva e dataRetirada
buscar reserva pelo idReserva

se reserva nao existir:
    retornar erro 404

se reserva.status for diferente de ATIVA:
    retornar erro de negocio

preencher dataRetirada
alterar reserva.status para RETIRADA
atualizar lote.status para RETIRADO
confirmar a transacao
```

---

### 6.4 Algoritmo de expiração de lote

**Objetivo:** identificar lotes cujo prazo de retirada venceu sem retirada confirmada.

```text
para cada lote com status DISPONIVEL ou RESERVADO:
    se dataAtual for maior que dataLimiteRetirada:
        alterar lote.status para EXPIRADO
```

Esse algoritmo pode ser executado por uma rotina agendada no backend.

---

### 6.5 Algoritmo de validação de destinação

**Objetivo:** impedir que o peso total destinado ultrapasse o peso originalmente registrado no lote.

```text
receber idLote, tipoDestinacao e pesoDestinacao
buscar lote pelo idLote
somar o peso das destinacoes ja registradas para o lote

se pesoJaDestinado + pesoDestinacao for maior que lote.pesoKg:
    retornar erro de negocio

criar destinacao
confirmar a transacao
```

A regra deve ficar no backend, pois envolve uma soma de múltiplos registros e precisa ser validada de forma transacional.

---

### 6.6 Algoritmo de validação de modalidade e preço

**Objetivo:** manter a consistência entre doação e venda.

```text
se modalidade for DOACAO e preco estiver preenchido:
    retornar erro de negocio

se modalidade for VENDA e preco for nulo ou menor ou igual a zero:
    retornar erro de negocio
```

Essa regra também é reforçada pela restrição `CK_RP_LOTE_PRECO` no banco Oracle.

---

### 6.7 Algoritmo de concessão de selo de parceiro

**Objetivo:** garantir consistência entre o selo do ofertante e sua data de concessão.

```text
se possuiSelo for verdadeiro:
    exigir dataSelo preenchida

se possuiSelo for falso:
    dataSelo deve ser nula
```

A regra é implementada pela restrição `CK_RP_OFERTANTE_SELO_DATA`.

---

### 6.8 Algoritmo de exclusão lógica

**Objetivo:** preservar o histórico de lotes, reservas e indicadores de impacto.

```text
receber entidade ativa
validar se a entidade possui historico relacionado

alterar ativo para N
nao excluir fisicamente o registro
```

A exclusão lógica é usada para ofertantes, beneficiários e pontos de distribuição.

> A seção 8.5 mostra como cada um desses algoritmos foi implementado no backend Java, incluindo as verificações adicionais.

## 7. Regras de integridade já implementadas no Oracle

| Regra | Implementação |
|---|---|
| Identificador único de cada registro | Chaves primárias com `IDENTITY`. |
| Relacionamentos válidos entre entidades | Chaves estrangeiras. |
| Tipos e status permitidos | Restrições `CHECK`. |
| Nome único de categoria | Restrição `UNIQUE` em `T_RP_CATEGORIA_ALIMENTO.nome`. |
| Selo e data do selo consistentes | `CK_RP_OFERTANTE_SELO_DATA`. |
| Preço coerente com a modalidade do lote | `CK_RP_LOTE_PRECO`. |
| Prazo de retirada posterior ao cadastro | `CK_RP_LOTE_DATAS`. |
| Uma reserva ativa por lote | Índice único condicional `UX_RP_RESERVA_ATIVA_LOTE`. |
| Retirada preenchida apenas para reserva retirada | `CK_RP_RESERVA_STATUS_DATA`. |
| Exclusão de alertas ao excluir lote sem dependências | Chave estrangeira de alerta com `ON DELETE CASCADE`. |

## 8. Backend Java (API REST)

O backend é uma API REST em Spring Boot que usa as tabelas acima sem nenhuma alteração. Ele também serve as telas web da solução.

### 8.1 Arquitetura em camadas

Pacote base: `br.com.fiap.redeprato`.

| Camada | Pacote | Responsabilidade |
|---|---|---|
| Model | `entity`, `entity.enums` | 9 entidades JPA, uma por tabela, e 10 enums com os mesmos valores dos `CHECK`. |
| DAO | `repository` | Interfaces Spring Data JPA com as consultas (filtros, somas e totais do painel). |
| BO | `service` | Regras de negócio e transações (`@Transactional`). |
| Controller | `controller` | 12 controllers REST com `GET`, `POST`, `PUT` e `DELETE`. |
| DTO | `dto` | Objetos de entrada e saída da API, separados das entidades. |
| Exception | `exception` | Exceções de negócio e um tratador global com respostas padronizadas. |
| Apoio | `converter`, `config` | Conversores de tipos, rotina agendada de expiração e dados de exemplo. |

### 8.2 Mapeamento entre tabelas e classes

- Cada coluna é mapeada com `@Column(name = ..., columnDefinition = ...)` usando exatamente o nome e o tipo do DDL (por exemplo, `VARCHAR2(100)`, `NUMBER(8,2)`, `CHAR(2)`).
- As chaves usam `@GeneratedValue(strategy = GenerationType.IDENTITY)`, aproveitando o `IDENTITY` do Oracle.
- Os campos `CHAR(1)` com `S`/`N` (`ativo`, `possui_selo`, `precisa_transporte`) viram `boolean` no Java por meio do conversor `BooleanSNConverter`.
- Os horários `VARCHAR2(5)` dos pontos (`HH:MM`) viram `LocalTime` por meio do conversor `LocalTimeHHMMConverter`, que valida o formato (regra 3 do DDL).
- Colunas `DATE` viram `LocalDateTime` (datas de lote, reserva, destinação e alerta) ou `LocalDate` (data do selo).
- No perfil Oracle, o Hibernate roda com `ddl-auto=validate`: ao iniciar, ele confere se todas as entidades batem com as tabelas e não altera nada no banco.

### 8.3 API REST

São **58 endpoints** (24 `GET`, 12 `POST`, 12 `PUT` e 10 `DELETE`). Todos começam com `/api` e trocam JSON.

| Recurso | Caminho base | Operações principais |
|---|---|---|
| Saúde | `/api/health` | Verifica se a API está no ar e qual banco está em uso. |
| Categorias | `/api/categorias` | CRUD completo; o nome é único. |
| Endereços | `/api/enderecos` | CRUD completo; filtro por bairro. |
| Ofertantes | `/api/ofertantes` | CRUD com exclusão lógica; concessão e retirada do selo (`/{id}/selo`). |
| Lotes | `/api/lotes` | CRUD; lista de disponíveis (`/disponiveis`); expiração manual (`/expirar`); destinação combinada (`/{id}/destinacoes`). |
| Beneficiários | `/api/beneficiarios` | CRUD com exclusão lógica. |
| Pontos de distribuição | `/api/pontos` | CRUD com exclusão lógica. |
| Reservas | `/api/reservas` | Criar, trocar local de retirada, cancelar (`/{id}/cancelar`), confirmar retirada (`/{id}/retirada`), excluir canceladas. |
| Destinações | `/api/destinacoes` | CRUD com controle do peso total por lote. |
| Alertas | `/api/alertas` | CRUD; aviso de xepa (`/xepa`); avisos recentes (`/recentes`). |
| Impacto | `/api/impacto` | Painel do ofertante (`/ofertantes/{id}`) e totais da rede (`/rede`). |
| Relatórios | `/api/relatorios` | Relatório mensal do ofertante (`/ofertantes/{id}/mensal`). |

A tabela completa, com exemplos de requisição e resposta, está em `docs/endpoints.md` no repositório do backend e na documentação interativa (`/swagger-ui.html`).

**Padrão de respostas:** `POST` devolve `201 Created` com o cabeçalho `Location`; `PUT` devolve `200 OK`; `DELETE` devolve `204 No Content`; listas vazias devolvem `200` com `[]`.

### 8.4 Funcionalidades adicionadas pelo backend

Além das operações básicas sobre as tabelas, o backend implementa:

| Funcionalidade | Como funciona |
|---|---|
| Expiração automática de lotes | Uma rotina agendada (`ExpiracaoJob`) roda a cada 5 minutos e marca como `EXPIRADO` os lotes vencidos. Também roda antes de listar lotes disponíveis e antes de criar uma reserva. |
| Lista de lotes disponíveis | Mostra só lotes `DISPONIVEL`, dentro do prazo e de ofertantes ativos, ordenados pelo prazo mais próximo, com filtros por categoria, modalidade e bairro. |
| Alerta automático de novo lote | Ao registrar um lote, o backend cria o alerta `NOVO_LOTE` na mesma transação. |
| Aviso de xepa em lote | O feirante avisa a xepa de vários lotes de uma vez, com novo prazo opcional; é criado um alerta `XEPA` por lote. Só feirantes ativos podem usar. O alerta pode ser desfeito. |
| Avisos recentes | Lista os alertas das últimas horas de lotes que ainda estão disponíveis, para a tela do beneficiário. |
| Troca do local de retirada | Uma reserva ativa pode trocar o ponto de distribuição ou voltar para a retirada no ofertante. |
| Confirmação de reserva | A consulta da reserva devolve o número de retirada, o endereço e o horário do local, o prazo e se o pagamento é feito na retirada (lotes de venda). |
| Destinação combinada | Registra de uma vez quanto do lote virou comida e quanto foi para a compostagem. |
| Painel de impacto do ofertante | Por mês: total de kg, kg consumidos e compostados, percentual de consumo, lotes retirados, beneficiários e pessoas atendidas, evolução por semana e situação do selo. |
| Totais da rede | Por mês: totais de toda a rede e ranking de ofertantes. |
| Relatório mensal | Para cada ofertante: lotes destinados no mês com data, alimento, peso, valor estimado e destino, com totais (apoio à documentação de doações). |
| Filtro de transporte | `GET /api/lotes?precisaTransporte=true` lista os lotes que precisam de transporte, base para a logística futura. |
| Dados de exemplo | Fora do Oracle, o `DataSeeder` cria dados com datas relativas ao dia atual para demonstração. |
| Telas web | Início, lotes disponíveis, registrar lote, retiradas e painel, servidas pelo próprio backend. |
| Acessibilidade | As telas foram verificadas contra as WCAG 2.2, nível AA, com axe-core e com o leitor de tela VoiceOver: atalho para pular o menu, foco visível, animação que pode ser pausada, alvos de toque com pelo menos 44 px e layout que funciona em telas de 320 px. |

### 8.5 Algoritmos da seção 6 no backend

| Algoritmo | Onde fica | Verificações adicionais do backend |
|---|---|---|
| 6.1 Criação de reserva | `ReservaService.criar` | Beneficiário precisa estar ativo; a expiração roda antes; o prazo do lote precisa estar no futuro; o ponto escolhido precisa estar ativo. Reserva e status do lote são gravados na mesma transação. |
| 6.2 Cancelamento de reserva | `ReservaService.cancelar` | Se o prazo do lote já passou, o lote vai para `EXPIRADO` em vez de voltar para `DISPONIVEL`. |
| 6.3 Confirmação de retirada | `ReservaService` (retirada) | A data de retirada é preenchida com a data e hora atuais. |
| 6.4 Expiração de lote | `LoteService.expirarVencidos` + `ExpiracaoJob` | Se o lote vencido estava `RESERVADO`, a reserva ativa dele é cancelada, mantendo a regra `CK_RP_RESERVA_STATUS_DATA` válida. |
| 6.5 Validação de destinação | `DestinacaoService` | A soma é recalculada também na correção de uma destinação, desconsiderando o próprio registro. |
| 6.6 Modalidade e preço | `LoteService` | Também valida peso maior que zero com até 2 casas decimais, valor estimado não negativo, prazo no futuro e URL da foto. Um lote só pode ser alterado enquanto está `DISPONIVEL`. |
| 6.7 Selo de parceiro | `OfertanteService.concederSelo` / `revogarSelo` | A data do selo é a data atual; ofertante inativo não recebe selo; quem já tem selo recebe erro 409. Ao retirar o selo, a data volta a ser nula. |
| 6.8 Exclusão lógica | `OfertanteService`, `BeneficiarioService`, `PontoDistribuicaoService` | `DELETE` marca `ativo = 'N'`; `PUT` com `"ativo": true` reativa. Categorias e endereços são excluídos fisicamente apenas quando não estão em uso. |

### 8.6 Tratamento de erros

Todas as respostas de erro têm o mesmo formato: data e hora, status, mensagem em português e caminho da requisição.

| Status | Quando |
|---|---|
| 400 | Regra de negócio violada, JSON inválido, parâmetro com tipo errado ou restrição `CHECK` do banco. |
| 404 | Registro ou rota não encontrados. |
| 409 | Conflito de estado (por exemplo, lote já reservado), registro duplicado (`ORA-00001`) ou exclusão de registro com dependências (`ORA-02292`). |
| 500 | Erro inesperado, sem expor detalhes técnicos. |

### 8.7 Perfis de execução

| Perfil | Banco | Comportamento |
|---|---|---|
| Padrão | H2 em memória, modo Oracle | Cria as tabelas automaticamente e carrega dados de exemplo. Usado nos testes e em demonstrações sem acesso ao Oracle. |
| `oracle` | Oracle da FIAP | Usa as tabelas criadas pelos scripts desta pasta, valida o mapeamento com `ddl-auto=validate` e não insere dados de exemplo. |

As credenciais do Oracle são lidas apenas de variáveis de ambiente (`ORACLE_URL`, `ORACLE_USERNAME`, `ORACLE_PASSWORD`) e nunca ficam no repositório.

### 8.8 Como executar com o Oracle

1. Execute os scripts DDL e DML na ordem da seção 4.
2. Defina as variáveis de ambiente e suba a aplicação:

   ```bash
   export ORACLE_URL=jdbc:oracle:thin:@oracle.fiap.com.br:1521:ORCL
   export ORACLE_USERNAME=<seu RM>
   export ORACLE_PASSWORD=<sua senha>
   export SPRING_PROFILES_ACTIVE=oracle
   ./mvnw spring-boot:run
   ```

3. Acesse `http://localhost:8080/api/health`. A resposta deve indicar `"profile":"oracle"`.
4. Abra `http://localhost:8080` para usar as telas.

## 10. Considerações finais

A modelagem da Rede de Prato foi construída para manter coerência entre o banco Oracle e as classes do backend Java. O banco armazena dados essenciais e reforça regras de integridade, enquanto o backend controla processos transacionais, como reserva, retirada, expiração e validação da soma das destinações.

Com essa estrutura, a solução possui uma base consistente para evoluir de um MVP acadêmico para uma plataforma de apoio à redução do desperdício alimentar.
